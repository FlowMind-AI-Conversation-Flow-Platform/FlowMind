# FlowMind 라피치 공고 적합도 체크리스트

## 1. 문서 목적

이 문서는 현재 `FlowMind` 프로젝트가 라피치 채용 공고의 직무 요구사항을 얼마나 충족하는지 점검하고, 무엇이 이미 맞아 있고 무엇이 아직 부족한지 명확히 정리하기 위한 평가 문서다.

평가 기준은 단순 아이디어 수준이 아니라 다음 세 가지를 구분해서 본다.

- `기획 적합성`: 문제 정의와 기능 구조가 공고와 맞는가
- `구현 적합성`: 실제 코드와 동작 결과로 증명 가능한가
- `포트폴리오 적합성`: 지원 시 경험으로 설득력 있게 설명 가능한가

현재 기준으로 FlowMind는 `기획 적합성은 높고`, `구현 적합성은 낮으며`, `포트폴리오 적합성은 구현을 진행해야 확보되는 상태`다.

## 2. 전체 판단 요약

### 현재 결론

- `방향성`: 공고와 매우 잘 맞는다
- `현재 상태`: 아직 문서 중심 단계다
- `판단`: 지금 당장은 `부분 충족`

즉, FlowMind는 라피치 공고에 맞는 프로젝트로 발전시키기 좋은 구조를 가지고 있지만, 아직은 "구현된 실무형 대화 시스템"보다 "잘 설계된 프로젝트 제안서"에 가깝다.

## 3. 공고 항목별 적합도 평가

### 3-1. Java 기반 웹 서비스 개발

- 현재 판정: `미충족`
- 이유:
  - 문서에는 `Spring Boot` 기반 백엔드를 계획하고 있다
  - 하지만 실제 Java 프로젝트, API, 서비스, DB 연동 코드가 아직 없다

### 3-2. 콜봇 플랫폼 연동 및 기능 개발

- 현재 판정: `미충족`
- 이유:
  - 콜봇/음성봇 운영 구조를 염두에 둔 대화 시스템 설계는 존재한다
  - 하지만 실제 외부 플랫폼 연동, STT 입력 처리, 음성 채널 연결, 콜봇 시뮬레이션은 없다

### 3-3. 시나리오/학습 빌더 등 툴을 이용한 인텐트 기반 대화형 시나리오 개발

- 현재 판정: `부분 충족`
- 이유:
  - Intent, Entity, Slot, Scenario, Dispatcher 개념이 문서로 잘 정리되어 있다
  - React Flow 기반 시나리오 빌더 방향도 제시되어 있다
  - 하지만 실제 빌더 UI와 시나리오 실행 엔진은 아직 구현되지 않았다

### 3-4. 챗봇, 콜봇 시나리오 설계 및 기획

- 현재 판정: `충족`
- 이유:
  - 하이브리드 대화 흐름이 명확하게 설계되어 있다
  - 정형 요청은 시나리오, 애매한 요청은 LLM fallback으로 보내는 구조가 잘 정의되어 있다
  - 대표 시나리오 예시와 슬롯 수집 흐름도 정리되어 있다

### 3-5. LLM 기반 프롬프트 설계 및 대화 시나리오 고도화

- 현재 판정: `부분 충족`
- 이유:
  - Prompt를 운영 자산으로 관리해야 한다는 방향이 잘 잡혀 있다
  - prompt template, active version, metrics, rollout 개념도 존재한다
  - 하지만 실제 prompt 파일, 버전 관리 로직, 품질 비교 결과는 아직 없다

### 3-6. 인텐트 기반 시나리오와 LLM 응답을 결합한 대화 구조 설계

- 현재 판정: `충족`
- 이유:
  - 이 프로젝트의 핵심 자체가 하이브리드 대화 구조다
  - `HybridDispatcher`, `ScenarioExecutor`, `LlmGateway`, `PromptAugmentationService` 같은 경계가 잘 정의되어 있다

### 3-7. 학습 데이터(STT/NLU) 분석 및 통합 관리

- 현재 판정: `미충족`
- 이유:
  - 분석 필요성은 문서에 있으나 실제 데이터 파이프라인이 없다
  - STT 원문 수집, 발화 라벨링, NLU 평가셋, 데이터 버전 관리 기능이 없다

### 3-8. Intent, Entity 제작 및 검증 등 관리

- 현재 판정: `부분 충족`
- 이유:
  - Intent, Utterance, Entity, Slot 정의 방식은 정리되어 있다
  - 하지만 실제 등록/검증/개선 플로우와 관리자 화면이 없다

### 3-9. 프롬프트/응답 결과 분석을 통한 품질 개선 및 리포트

- 현재 판정: `부분 충족`
- 이유:
  - conversation log, fallback reason, prompt version, latency 같은 지표 설계는 있다
  - 하지만 실제 데이터 저장, 대시보드, 리포트 기능은 아직 없다

## 4. 현재 프로젝트의 강점

FlowMind는 공고와 연결했을 때 아래 강점이 분명하다.

- `Intent + Scenario + LLM Fallback` 구조가 직무와 직접 맞닿아 있다
- 단순 챗봇이 아니라 운영 가능한 시스템으로 접근하고 있다
- Prompt Engineering과 Context Engineering을 분리해서 다루고 있다
- 로그, 지표, 개선 루프까지 고려하고 있다
- 추후 콜봇/음성봇 영역으로 확장하기 좋은 구조다

즉, 구현만 따라오면 라피치 공고에 대한 설명력이 높은 프로젝트가 될 가능성이 크다.

## 5. 현재 프로젝트의 약점

반대로 지금 단계에서 부족한 점도 분명하다.

- 실제 코드가 없다
- Java 웹 서비스 증빙이 없다
- 콜봇 플랫폼 연동 증빙이 없다
- STT/NLU 데이터 분석 경험으로 연결할 산출물이 없다
- 품질 개선 리포트나 운영 지표 결과가 없다

이 다섯 가지가 해결되지 않으면 지원서에서 "직무와 잘 맞는 프로젝트를 설계했다"까지만 말할 수 있고, "직접 구현하고 운영 관점까지 검증했다"로는 연결되기 어렵다.

## 6. 라피치 공고 기준 최종 판정

현재 FlowMind는 아래처럼 정리할 수 있다.

- `기획 관점`: 충족
- `아키텍처 설계 관점`: 충족
- `실제 구현 관점`: 미충족
- `포트폴리오 설득력 관점`: 부분 충족

따라서 현재 시점의 최종 판정은 `부분 충족`이다.

## 7. 통과 기준

이 프로젝트가 라피치 공고를 실질적으로 만족한다고 보기 위한 최소 기준은 아래와 같다.

- Spring Boot 기반 API 서버가 동작한다
- Intent 3~5개, Entity/Slot, Scenario 1~2개가 실제로 동작한다
- LLM fallback 1개가 실제 OpenAI API와 연결된다
- conversation log와 dispatch trace가 저장된다
- prompt template 또는 prompt file 기반 관리 구조가 존재한다
- 간단한 운영 지표 화면 또는 리포트가 존재한다
- 음성/콜봇 확장 가능성을 보여주는 입력 흐름 또는 외부 연동 모의 구현이 있다

이 기준까지 가야 "공고 내용과 맞는 프로젝트를 실제로 만들었다"고 설명할 수 있다.
