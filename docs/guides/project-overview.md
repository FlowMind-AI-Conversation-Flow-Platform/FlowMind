# FlowMind 프로젝트 상세 설명

## 1. 프로젝트 한 줄 정의

FlowMind는 `규칙 기반 Intent 처리`와 `LLM 기반 자연어 대응`을 결합한 하이브리드 대화 플랫폼이다.

이 프로젝트의 목적은 단순히 "챗봇을 만든다"가 아니다. 실제 서비스 운영에서 자주 부딪히는 문제, 즉 다음 세 가지를 동시에 해결하는 것이 목표다.

- 반복적이고 명확한 요청은 빠르고 안정적으로 처리할 것
- 애매하거나 감정이 섞인 요청은 유연하게 대응할 것
- 모든 대화 결과를 데이터로 남겨 지속적으로 개선할 것

## 2. 왜 이 프로젝트가 필요한가

고객 응대 시스템은 보통 두 방향 중 하나로 치우친다.

### 규칙 기반 시스템의 장점과 한계

규칙 기반 시스템은 운영 통제가 쉽다.

- 어떤 질문이 어떤 시나리오로 가는지 명확하다
- 응답이 예측 가능하다
- 민감한 업무를 안정적으로 처리할 수 있다

하지만 한계도 분명하다.

- 표현이 조금만 달라져도 인식 실패가 발생한다
- 예상하지 못한 질문에 약하다
- 맥락이 이어지는 대화에서 경직되기 쉽다

### LLM 기반 시스템의 장점과 한계

LLM 기반 시스템은 유연하다.

- 다양한 표현을 이해할 수 있다
- 애매한 질문에도 자연스럽게 반응할 수 있다
- 불만, 감정 표현, 맥락 의존 질의에 강하다

하지만 운영 관점에서는 단점이 있다.

- 응답 통제가 어렵다
- 품질이 일관되지 않을 수 있다
- 비용과 지연시간이 발생한다
- 구조화된 액션으로 이어지기 어렵다

### FlowMind의 접근

FlowMind는 둘 중 하나를 선택하지 않는다.

- `정확성과 통제`는 규칙 기반 엔진이 담당한다
- `유연성과 자연스러움`은 LLM이 담당한다
- 두 시스템 사이의 선택은 `Context + Confidence`를 기준으로 결정한다

즉, FlowMind는 "하이브리드 대화 운영 시스템"이다.

## 3. 무엇을 만드는 프로젝트인가

FlowMind는 크게 다섯 가지 층으로 구성된다.

### 3-1. Context Layer

사용자의 발화만 보는 것이 아니라, 그 발화가 어떤 맥락에서 나왔는지 함께 본다.

- 사용자 정보: 채널, 언어, 고객 등급, 계정 기간
- 세션 정보: 이전 대화, 현재 진행 중인 의도, 이미 수집된 슬롯
- 도메인 정보: 통신, 금융, 커머스 등 업무 영역별 공통 규칙

이 층의 목적은 발화를 더 정확하게 해석하는 것이다.

예를 들어 `"지난 달은?"`이라는 입력은 단독으로 보면 애매하지만, 직전에 `"요금 조회"`가 진행 중이었다면 기간 슬롯에 대한 후속 답변으로 해석할 수 있다.

### 3-2. Intent Layer

사용자의 입력을 특정 업무 의도로 분류한다.

예:

- `"요금 조회하고 싶어요"` -> `BILLING_INQUIRY`
- `"카톡으로 요금표 보내줘"` -> `SEND_DOCUMENT_KAKAOTALK`
- `"결제 방법 바꾸고 싶어요"` -> `CHANGE_PAYMENT_METHOD`

이 단계에서는 단순 키워드뿐 아니라 다음 정보를 함께 본다.

- 이전 의도와의 연속성
- 채널 특성
- 엔티티 존재 여부
- 요구 슬롯 충족 여부

이 레이어는 "무슨 요청인지"를 결정한다.

### 3-3. Scenario Layer

의도가 충분히 명확하고 안전하게 자동화할 수 있다면, 시스템은 LLM으로 가지 않고 시나리오를 실행한다.

시나리오는 노드 기반 플로우로 구성된다.

- 시작 노드
- Intent 확인 노드
- 슬롯 수집 노드
- 액션 실행 노드
- 종료 노드

예를 들어 요금 조회 흐름은 다음처럼 구성할 수 있다.

1. 고객이 `"요금 조회"` 요청
2. 전화번호가 없으면 요청
3. 기간 정보가 없으면 요청
4. 조회 실행
5. 결과 응답

이 레이어는 "무엇을 어떤 순서로 처리할지"를 담당한다.

### 3-4. LLM Fallback Layer

의도 분류 결과가 불확실하거나, 사용자의 표현이 복합적이거나, 규칙 기반으로 대응하기 어려운 경우 LLM으로 넘긴다.

단, 아무 정보 없이 LLM을 호출하지 않는다.

LLM에는 다음과 같은 정보가 함께 전달된다.

- 사용자 등급과 채널
- 현재 세션 요약
- 이미 수집된 슬롯
- 추정 의도와 신뢰도
- 현재 활성 프롬프트 템플릿

이렇게 하면 LLM 응답이 더 안정적이고 서비스 맥락에 맞게 나온다.

이 레이어는 "규칙 엔진이 처리하지 못하는 영역을 안전하게 보완"하는 역할이다.

### 3-5. Ops & Analytics Layer

FlowMind의 핵심 가치는 단순 응답 생성이 아니라 운영 가능성에도 있다.

대화가 끝나면 다음 정보가 기록된다.

- 어떤 경로로 응답했는가 (`SCENARIO` 또는 `LLM`)
- 분류 신뢰도는 어땠는가
- 어떤 프롬프트 버전을 사용했는가
- 응답시간은 얼마였는가
- 사용자가 만족했는가

이 데이터는 다음 개선으로 이어진다.

- 실패가 많은 Intent 보완
- 미매칭 발화 분석
- Prompt 버전 비교
- Fallback 비율 최적화

즉, FlowMind는 대화 시스템이면서 동시에 학습하는 운영 도구다.

## 4. 사용자 입력이 처리되는 전체 흐름

FlowMind의 핵심 흐름은 아래와 같다.

1. 사용자가 질문을 보낸다
2. 시스템이 사용자/세션/도메인 컨텍스트를 불러온다
3. 입력을 Intent와 Entity 기준으로 분석한다
4. 신뢰도를 계산한다
5. 신뢰도가 높으면 시나리오 엔진이 실행된다
6. 신뢰도가 낮으면 프롬프트가 보강된 상태로 LLM을 호출한다
7. 결과를 사용자에게 응답한다
8. 전체 로그를 저장하고, 이후 분석 데이터로 사용한다

이 구조의 장점은 명확하다.

- 정형 업무는 빠르고 싸게 처리할 수 있다
- 비정형 요청은 유연하게 처리할 수 있다
- 어떤 판단이 왜 일어났는지 추적할 수 있다

## 5. 이 프로젝트의 핵심 설계 철학

### 5-1. LLM을 중심이 아니라 보조 축으로 둔다

FlowMind는 "모든 것을 LLM으로 해결"하는 구조를 지향하지 않는다.

그 이유는 다음과 같다.

- 비용이 불필요하게 커진다
- 구조화된 업무 처리에 불리하다
- 서비스 일관성이 떨어진다

따라서 LLM은 fallback과 유연한 표현 처리에 집중한다.

### 5-2. Context를 별도 자산으로 본다

대부분의 대화 시스템은 사용자 입력 문자열 자체만 본다. FlowMind는 맥락을 독립된 자산으로 본다.

- 사용자 컨텍스트
- 세션 컨텍스트
- 도메인 컨텍스트

이 구조는 의도 분류 정확도와 대화 연속성을 높이는 핵심이다.

### 5-3. Prompt를 문자열이 아니라 운영 대상 자산으로 본다

Prompt는 코드 안에 박아 넣는 문장이 아니라, 버전 관리와 실험이 가능한 운영 대상이다.

- 버전 생성
- 활성 버전 관리
- A/B 테스트
- 성능 측정

이렇게 해야 LLM 응답 품질을 개선할 수 있다.

### 5-4. 모든 결정은 로그로 남아야 한다

FlowMind에서는 응답 그 자체보다 "왜 이 경로로 갔는가"가 중요하다.

그래서 최소한 아래는 로그로 남겨야 한다.

- 분류 결과
- confidence
- route
- 사용 프롬프트
- 응답시간
- 사용자 평가

## 6. 실제로 어떤 화면과 기능이 생기게 되는가

이 프로젝트가 완성되면 운영자는 대략 다음 기능을 사용하게 된다.

### 시나리오 빌더

- 노드 기반으로 업무 플로우 생성
- 분기, 수집, 액션, 종료 설계
- React Flow 기반 편집

### Intent Studio

- Intent 등록
- 예문 관리
- 슬롯 정의
- 필수 엔티티 설정

### Prompt Ops

- 프롬프트 버전 생성
- 활성 버전 교체
- 테스트 대상 비교
- 응답 품질 분석

### Analytics

- Intent 정확도 추이
- Scenario / LLM 라우팅 비율
- 평균 응답시간
- 만족도 분포
- 실패 지점 분석

### Data Lab

- 미매칭 발화 수집
- 자주 실패하는 질문 확인
- 새 Intent 후보 발견
- 예문 데이터 보강

## 7. 어떤 기술 스택이 적합한가

현재 기준으로 이 프로젝트에는 다음 구성이 가장 현실적이다.

### 프론트엔드

- `Vercel` 배포
- `React + Vite + TypeScript`
- `React Flow` for scenario builder
- `Zustand` for lightweight state management

### 백엔드

- `Spring Boot`
- `PostgreSQL`
- `Redis`
- `Flyway`

### LLM 연동

- OpenAI `Responses API`
- 공식 Java SDK `openai-java`

### 로컬 개발

- `Docker Compose`

이 조합은 구현 난이도, 운영 편의성, 포트폴리오 전달력의 균형이 좋다.

## 8. MVP에서 꼭 필요한 범위

처음부터 모든 기능을 만들 필요는 없다. MVP는 아래 정도가 적절하다.

- Intent 3~5개
- 대표 시나리오 1~2개
- 슬롯 수집 가능한 흐름 1개
- LLM fallback 1개
- prompt file 기반 템플릿 관리 최소 기능
- 대화 로그 저장
- 기본 Analytics 3~4개 지표

즉, "전체 플랫폼 완성"이 아니라 "하이브리드 구조가 실제로 동작한다"를 증명하는 수준이 MVP다.

## 9. 이 프로젝트가 포트폴리오로 좋은 이유

FlowMind는 단순 CRUD나 단순 챗봇보다 보여줄 수 있는 폭이 넓다.

- 백엔드 아키텍처 설계
- 대화 모델링
- 상태 관리
- 데이터 기반 운영 설계
- 프롬프트 실험 체계
- 시각적 시나리오 빌더 UI

즉, 기술 구현뿐 아니라 서비스 운영 감각까지 함께 보여줄 수 있다.

이 점이 이 프로젝트의 가장 큰 강점이다.

## 10. 현재 단계에서 가장 중요한 것

지금 이 프로젝트에서 가장 중요한 것은 기능을 많이 만드는 것이 아니다.

먼저 아래를 명확히 해야 한다.

- 어떤 문제를 해결하는 프로젝트인가
- 어떤 요청은 규칙 기반으로 처리할 것인가
- 어떤 요청은 LLM으로 넘길 것인가
- 그 판단 기준을 어떻게 기록하고 개선할 것인가

이 문서의 목적은 바로 그 기준을 정리하는 것이다.

다음 단계에서는 이 설명을 바탕으로 페이즈 단위 로드맵과 실제 초기 프로젝트 구조를 만든다.
