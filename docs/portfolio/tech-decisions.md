# FlowMind Tech Decisions

## 목적

이 문서는 나중에 "왜 이런 기술과 구조를 선택했는가"를 설명하기 위한 자료다.

## 1. 왜 Spring Boot인가

- Java 기반 웹 서비스 역량을 직접 보여주기 좋다
- 실무형 백엔드 구조를 설명하기 쉽다
- JPA, Flyway, PostgreSQL, Redis와 조합이 안정적이다
- 실제 bootstrap 구현 단계에서 health, 설정, migration 구조를 빠르게 검증하기 좋다

## 2. 왜 하이브리드 구조인가

- 규칙 기반 처리만으로는 자연어 변형과 맥락 의존 요청 대응이 어렵다
- LLM 단독 구조만으로는 서비스 통제와 일관성 확보가 어렵다
- 그래서 deterministic scenario와 LLM fallback을 분리했다

## 3. 왜 prompt file 기반 템플릿 관리인가

- 프롬프트를 코드 문자열로 두면 변경 추적과 실험이 어렵다
- 파일로 분리하면 버전 관리와 리뷰가 쉬워진다
- 이후 `prompt_template` 테이블로 확장하기 쉽다

## 4. 왜 dispatch trace를 남기려 하는가

- 중요한 것은 "무슨 답을 했는가"보다 "왜 그 route로 갔는가"다
- 잘못된 분기, fallback 과다, prompt 품질 저하를 추적하려면 판단 과정 로그가 필요하다

## 5. 왜 phase / execution plan 구조를 쓰는가

- 구현 전에 범위와 완료 기준을 명확히 할 수 있다
- 하네스 엔지니어링 방식에 맞게 문서를 system of record로 유지할 수 있다
- 나중에 포트폴리오 정리 시 작업 과정을 설명하기 쉽다

## 면접에서 강조할 포인트

- 단순 기술 나열이 아니라 "서비스 운영 문제"에서 출발한 선택이었다는 점
- 비용, 품질, 통제, 확장성의 균형을 고려했다는 점
